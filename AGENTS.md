# Materials Studio Agent Rules

## Goal
Build reproducible Materials Studio modeling workflows through MCP tools, with optional live GUI loading into the currently open Materials Studio session.

## Hard Rules
- Prefer MaterialsScript and file-based workflows for structural changes.
- Use GUI control only when the user explicitly asks for the open Materials Studio GUI or real-time visual feedback.
- Prefer `material_studio_gui_*` tools for GUI preflight, activation, snapshots, opening structures, and Copy Script assistance.
- For crystallographic or semiconductor viewport replay, call `material_studio_gui_prepare_view_replay` first. It only persists camera/projection parameters and safety state; it does not modify the GUI.
- After Computer Use, reviewed Copy Script, or human review applies a prepared view, call `material_studio_gui_record_view_replay` for that exact view. Do not treat the replay as accepted unless the returned target revision identity and single-window gates pass.
- When a restricted @mcp allowlist exposes only the high-level entry, persist prepared-view evidence through `material_studio_live_modeling_request.view_replay_confirmation`. Supply the view name, observed current revision, exact window handle/title, camera-manifest result, and the reviewed native command ID when one was used. A binding mismatch must not append a replay event or create a revision.
- Read each prepared view's `execution_recipe` and the manifest/status `replay_continuation` before GUI input. Automatic replay is allowed only when `automation_ready=true`. In Materials Studio 20.1, the verified face recipes are: `front` = named Reset View; `back` = Reset + unmodified `Left x4`; `right` = Reset + `Up x2, Left x2`; `left` = Reset + `Up x2, Right x2`; `top` = Reset + `Up x2`; `bottom` = Reset + `Left x4, Down x2`. The verified isometric recipe is Reset, then `45 degrees: Up x2, Left x3`, then `35.26438968 degrees: Down x1`; it must finish with A left-down, B right-down, C up, restore `numNudgeAngle=45`, preserve `numNudgeFactor=2.0`, and close Movement. Record exact `keyboard_stages`, reset/restoration/control evidence, and `modifier_keys=[]`. Never hold Shift: MS documents Shift+arrow as rotating selected objects, which changes geometry. `crystal_plane_*` may be automatic only when the returned recipe verifies the installed Miller Plane, Tree Explorer, Properties Explorer, and View Onto commands/help. Create exactly one transient plane, isolate its exact Object Tree leaf by before/after diff, select only the semantic item rectangle, verify Properties Explorer, capture the aligned view, then undo only whitelisted View Onto/Create Plane actions and prove the document, tree, view baseline, and structure SHA-256 were restored. Record `miller_plane_evidence`; treat the camera match as plane-normal plus MS native smallest-acute-angle roll, not exact analytic `camera_up`/`camera_right`. A `crystal_*` lattice-direction view may use the same transient-plane path only when its recipe reports `exact_integer_plane_collinear`; use the returned mapped Miller indices, require `direct_lattice_direction_matches_manifest=true`, and never assume same-index `[uvw]=(hkl)`. Non-collinear directions remain reviewed-camera-backend gated. Never substitute continuous Spin/Roll/Rock, `cmdNudge*`, object-align commands, or blind trackball drags.
- On resumed sessions, read `material_studio_live_project_status.gui_view_replay` before replaying views; it reports the manifest, accepted-view progress, last event, and continuation action for the current revision.
- Explicit continuation requests such as `continue the next GUI view replay`, `resume view replay`, `继续视角回放`, or `继续验证下一个 GUI 视角` should route through `material_studio_live_modeling_request` with `workflow=continue_view_replay`. That workflow may prepare/upgrade the manifest but never creates a revision or issues GUI input; execute a returned recipe only after inspecting its automation gate.
- Materials Studio 20.1 locally documents Reset/Recenter/View Onto/View Across/Fit-to-View but no arbitrary camera-vector MaterialsScript API. Do not invent one. A pre-activation screenshot can capture an occluding window, so activate and reverify the target wrapper before screenshot or input; never use unnamed toolbar controls or blind coordinates.
- `material_studio_gui_status` may omit `project_id`/`revision`; when a latest current structured project exists, use its `project_resolution`, `target_window`, and `target_window_resolution` fields rather than assuming `selected_window_handle` is the current revision.
- In multi-window sessions, prefer `material_studio_gui_status.window_management` for the compact decision receipt: it reports process/window counts, selected-window versus target-window identity, wrapper metadata coverage, ambiguity warnings, and the recommended next GUI tool.
- Treat `model_ready_for_hotload` as artifact readiness only, never as permission to execute a GUI hot-load. `safe_to_attempt_hotload` and `same_window_hotload_ready` may be true only after live GUI status was probed, a Materials Studio window was found, and `single_window_policy_ok=true`.
- When `include_gui_status=false` or the single-window state is otherwise unverified, require `gui_preflight_required=true`, keep hot-load safety false, and call the returned read-only `material_studio_gui_status` payload before any apply-current or open-structure action. Preserve the deferred execute action for after preflight; do not launch a new process to satisfy this gate.
- `material_studio_gui_launch`, `material_studio_gui_activate`, and `material_studio_gui_copy_script_assist` may also omit `project_id`/`revision`; when possible they resolve the latest current structured project and target that wrapper window instead of an arbitrary older Materials Studio window.
- If preflight reports `preview_ready_gui_not_open` and `recommended_tool=material_studio_gui_launch`, use it only when starting a new GUI session is intentional; otherwise activate an already-open Materials Studio window and rerun preflight.
- Do not implicitly launch a new `MatStudio.exe` from hot-load, apply-current, or `material_studio_gui_open_structure`; reuse the existing window/project. On Windows, the local fallback may drive the existing window's File/Open dialog to load the generated workspace `.stp` wrapper; if that same-window dialog path cannot be controlled, return `gui_open_warning` and keep the generated structure/report artifacts.
- A single-process startup session may expose `Materials Studio File Associations`, `New Project`, and `Welcome to Materials Studio` dialogs. The Windows fallback may dismiss the file-association dialog, cancel only the empty `New Project` save dialog, and use the welcome page's `Browse...` file picker to open the exact generated `.stp`; never trust a directly written welcome-page path while a stale Recent Projects item remains selected. Unknown modal dialogs must still block hot-loading.
- If preflight reports `ready_for_live_edit_gui_review` and `recommended_tool=material_studio_gui_open_structure`, reload the returned latest-project `structure_path` into Materials Studio and snapshot it before claiming the GUI shows the current revision.
- If preflight reports `ready_for_live_edit_gui_activation` and `recommended_tool=material_studio_gui_activate`, call it with the returned `project_id`, `revision`, and `take_snapshot=true`; do not re-hot-load the structure just to bring the already-loaded target revision window forward.
- `material_studio_gui_apply_current_revision` may omit `project_id` to apply the latest current project; it still previews by default and executes only with explicit `execution_mode="execute"`.
- `material_studio_gui_snapshot` may omit `project_id` and `revision` for ongoing sessions; when it resolves the latest current project, surface `project_resolution` and use the returned project/revision-scoped screenshot and GUI log as the persisted visual evidence.
- For generated structures, GUI open tools wrap the output in a workspace `.stp` project before loading it so Materials Studio has an active project.
- GUI open waits for the MCP wrapper project name to appear in a Materials Studio window title before treating the open as strongly settled; if the wrapper title is not observed, preserve weaker `window_identity_verification=unverified` evidence.
- When using `material_studio_gui_open_structure` for a structured revision, pass `project_id` and `revision` when available; if `project_id` is supplied and `revision` is omitted it uses that project's current revision, and if `project_id` is omitted it only syncs diagnostics when `structure_path` matches the latest current revision's planned structure. By default it persists `view_audit`, `modeling_health`, `modeling_report`, and `report.json` for that GUI-open artifact.
- Start live @mcp sessions with `material_studio_live_session_preflight` when runner, GUI, workspace, latest-project, or next-tool readiness is uncertain.
- Use `ms-mcp-live-smoke` for local command-line acceptance checks of the same live workflow; default scenarios are preview-safe, while `--hotload` or `--execution-mode execute` intentionally materializes and opens the structure in Materials Studio.
- Prefer `material_studio_live_modeling_request` as the high-level @mcp entry point when the user gives a modeling request and a structured `ModelSpec` or `SemanticPatch` can be supplied.
- After changing MCP registration, tool schemas, annotations, or the example Codex config, run `ms-mcp-protocol-smoke --cwd . --config .codex/config.toml.example`. Direct Python calls alone do not prove that an @mcp client can initialize the server, discover the tools, and call them over stdio.
- The protocol smoke config audit is read-only. Report active `.codex/config.toml` drift, but never rewrite the user's active config automatically.
- Before claiming that `@mcp` is available in the current Codex session, run `ms-mcp-config-doctor --cwd .` against the active config and require `config_ready=true`, then restart Codex if the server is not already visible. The doctor may write only a separate review snippet and must refuse the active config path; merge config changes only with explicit user approval.
- Use `material_studio_live_project_status` to summarize the current revision, generated script, output structure, persisted `view_audit.json`, computed diagnostics, GUI status, and next action.
- If `project_resolution.current_pointer_recovery_used=true`, surface the returned `current_pointer` receipt. Recovery must read the newest valid immutable revision without rewriting the malformed or missing `current.json`, creating a revision, or deleting orphan files. Read-only inspection may continue; the next explicitly requested successful revision write may atomically repair the pointer and must choose a revision number above every existing revision filename.
- `material_studio_live_project_status` preserves `diagnostic_export_requested` from persisted reports so resumed sessions know whether diagnostic artifacts were explicitly requested.
- `material_studio_live_project_status` also preserves `normality_check_requested` when a prior create/patch/show request explicitly asked to check whether the model is normal.
- `material_studio_live_project_status` may omit `project_id` to summarize the latest current project; surface `project_resolution` when doing so.
- `material_studio_live_modeling_request` also handles current-model inspection requests such as `Is the current model normal?` and diagnostic export requests such as `export current view parameters` or `导出当前模型视角参数`; these route to live status or view-bundle export without creating a new revision.
- If a request combines GUI display with diagnostics, such as `show the current model in Materials Studio and export current view parameters`, keep the GUI hot-load path active and return `diagnostic_export_requested=true` plus `view_bundle_manifest_path` instead of downgrading it to diagnostics-only.
- Chinese current-model display requests such as `把这个模型推到当前 MS 窗口，同时导出视角参数` and `重新热加载当前 revision` should route through `workflow=show_current`; the first should execute and export diagnostics, and neither should create a new revision.
- `material_studio_project_history` and `material_studio_project_rollback` may omit `project_id` for ongoing sessions; surface `project_resolution` when the latest current project is selected.
- Chinese session control requests such as `撤销上一步并热加载到 Materials Studio`, `回退到上一个 revision 并热加载`, `重做刚才撤销的修改并热加载`, and `恢复 r000 并热加载到 MS` should route through rollback/redo/restore before show-current; rollback and restore create a new revision and never delete history.
- Use `material_studio_live_capabilities` when deciding whether a natural-language request can be handled by local templates, local patch commands, or a reviewed schema payload.
- Use `material_studio_live_capabilities.diagnostics.diagnostic_focus_profiles` to map semiconductor diagnostic requests to required summary fields, CSV artifact keys, example prompts, and the `requested_diagnostic_focus_status` receipt before promising that a diagnostic bundle covers a requested focus.
- For semiconductor live responses and status reports, prefer the returned `modeling_report.recommended_diagnostic_focuses`, `modeling_report.unrequested_recommended_diagnostic_focuses`, and `live_summary.recommended_diagnostic_focuses` fields to explain the template-specific checks still recommended for the model; keep them distinct from `requested_diagnostic_focuses`, which only records diagnostics explicitly asked for by the user.
- If the user gives only natural language, call `material_studio_live_modeling_request` first for supported local templates; if it returns `nl_plan.kind="unsupported"`, translate the request into a reviewed `ModelSpec` or `SemanticPatch`.
- When a create or patch request also asks to export view/model diagnostics, surface `diagnostic_export_requested=true` in both the live response and `modeling_report`; `view_bundle_manifest_path` remains the stable artifact entry point.
- When a create, patch, rollback, redo, restore, show, or inspect request explicitly asks whether the model is normal, surface `normality_check_requested=true` and `diagnostic_export_requested=true` in the response, `modeling_report`, and `change_receipt`; still base the answer on exported view-bundle diagnostics, `modeling_health.verdict`, `modeling_report.normality`, and semiconductor/view review fields.
- For semiconductor modeling requests, prefer the semiconductor local templates exposed in `material_studio_live_capabilities.domain_focus.semiconductor_template_profiles` before building a custom crystal spec. Use each profile's `default_diagnostic_focuses`, material/interface/surface metadata, and `execute_backend` to choose the right hot-load and diagnostic path. Current examples include Si diamond cubic, Si p-n junction, Ge diamond cubic, 3C-SiC, 4H-SiC, and 6H-SiC bulk, c-BN zinc blende, ZnO wurtzite, beta-Ga2O3 monoclinic bulk, 2D MoS2/WS2/MoSe2/WSe2 monolayers, CdTe zinc blende, ZnS zinc blende, ZnSe zinc blende, ZnTe zinc blende, CdS zinc blende, CdSe zinc blende, Si/Ge(001) heterostructure or MQW start, Si/SiO2(100) semiconductor-oxide, Al/SiO2/Si and Al/SiO2/4H-SiC MOS capacitor/gate-stack, TiN/HfO2/Si high-k MOS capacitor/gate-stack, Cu/SiO2(100) metal-oxide interface, Al/Si(100), metal/ZnO(0001), metal/beta-Ga2O3(010), and metal/4H-SiC(0001) Si-face Schottky metal-semiconductor contacts, GaAs zinc blende, AlAs zinc blende, AlP zinc blende, AlSb zinc blende, GaP zinc blende, GaSb zinc blende, InP zinc blende, InAs zinc blende, InSb zinc blende, GaAs/AlAs(001) and InGaAs/InP(001) heterostructure or MQW starts, Al0.25Ga0.75N/GaN(0001) heterostructure or HEMT/MQW start, AlN/GaN(0001) heterostructure or HEMT/MQW start, In0.25Ga0.75N/GaN(0001) quantum-well/MQW start, GaN wurtzite, AlN wurtzite, InN wurtzite, Si(100) slab, GaAs(001) slab, GaN(0001) slab, AlN(0001) slab, InN(0001) slab, ZnO(0001) slab, and centered beta-Ga2O3(010) slab.
- For crystal `ModelSpec` execution, MaterialsScript lattice construction remains preview-only; explicit `execution_mode="execute"` materializes a CIF artifact and can hot-load that CIF into the GUI.
- Supported local new-structure templates include common monosubstituted benzenes such as nitrobenzene, phenol, aniline, and toluene; do not downgrade those requests to plain benzene.
- Chinese live requests are supported for common molecule and semiconductor templates plus hot-loading phrases, for example `构建硝基苯并准备预览`, `构建水分子并热加载到 Materials Studio`, `构建硅晶体并热加载到 Materials Studio`, `构建硅晶体并实时热加载到当前界面，导出视角参数并检查模型是否正常`, `构建硅晶体，让我在 MS 里看到变化`, `推送到当前窗口`, `构建硅 PN 结并热加载到 Materials Studio`, `构建砷化镓晶体并热加载到 Materials Studio`, `构建二硫化钼单层并热加载到 Materials Studio`, `构建硒化锌晶体并热加载到 Materials Studio`, `构建 2x1x1 硅超胞并掺杂 P，然后热加载到 Materials Studio`, and `把它变成硝基苯`.
- Chinese semiconductor device and polytype starts such as `构建4H碳化硅晶体并热加载到 Materials Studio`, `构建6H碳化硅晶体并热加载到 Materials Studio`, and `构建硅 MOS 电容并热加载到 Materials Studio` should route to `silicon_carbide_4h_hexagonal`, `silicon_carbide_6h_hexagonal`, and `aluminum_silicon_dioxide_silicon_mos_capacitor`, not the generic 3C-SiC path.
- The reviewed 6H-SiC template covers P63mc bulk only. Explicit 6H-SiC slab, surface-structure, MOS, interface, heterostructure, or metal-contact requests must remain unsupported until a reviewed derived-geometry template exists; never silently substitute 3C-SiC, 4H-SiC, or Si.
- Chinese metal/semiconductor contact starts such as `构建金属-半导体接触并热加载到 Materials Studio` and `构建金半接触` should route to `aluminum_silicon_100_schottky_contact`; requests with `接触诊断` should include `metal_semiconductor_contact` diagnostics.
- Prefer `material_studio_live_update_with_patch` for user-requested live updates: convert the natural-language change to a `SemanticPatch`, validate it, create a new revision, optionally execute, open it in GUI, and export view-audit diagnostics.
- `material_studio_live_update_with_patch` may omit `project_id` and `base_revision` for ongoing sessions; it resolves `patch.project_id` or the latest current project, defaults to that current revision, and surfaces `project_resolution`.
- In `material_studio_live_update_with_patch`, an omitted `execution_mode` may auto-resolve to execute only for explicit hot-load/live GUI text; explicit `execution_mode="preview"` must override hot-load text.
- Use Computer Use for menu and viewport interaction when available. If it is unavailable, use the local GUI fallback tools and report the limitation.
- After Computer Use or a human reviewer actually observes the current model in the Materials Studio viewport, persist the evidence through `material_studio_live_modeling_request.visual_confirmation` or `material_studio_gui_record_visual_confirmation`. Supply the observed `expected_revision`, `expected_window_handle`, and exact wrapper `expected_window_title`; mismatched, non-current, metadata-free, or multi-window targets must be rejected. Visual confirmation never repairs structural, semiconductor, acceptance, or calculation-readiness failures.
- Never overwrite user input files. Write generated files into the configured workspace.
- Every job should emit `spec.json` or revision JSON, a generated script when applicable, `stdout.log`/`stderr.log` or runner metadata, `report.json`/audit JSON, and a final structure if available.
- Validate structures before launching expensive calculations.
- For Materials Studio version differences, trust Copy Script output over guessed API calls.
- For natural-language modeling, prefer structured `ModelSpec` and `SemanticPatch` tools.
- Default structured workflows to `execution_mode=preview`; execute only after explicit user confirmation, except when the user has explicitly requested live hot-loading.
- In `material_studio_live_modeling_request`, an omitted `execution_mode` may auto-resolve to execute only for explicit hot-load or GUI-display text such as "hot-load", "real-time GUI", "push it to MS", "let me see it in MS", "实时热加载", "推送到当前窗口", or "让我在 MS 里看到变化"; inspect `execution_mode_source` before reporting why execution happened.
- Do not call `material_studio_run_script` unless the user explicitly asks for custom script execution.
- For follow-up modifications, load current project state and apply a semantic patch instead of rebuilding from scratch.
- Normality, semiconductor-health, acceptance, or calculation-readiness failures must not prevent a valid current `ModelSpec` from accepting a corrective `SemanticPatch`. Preserve those trust blockers, create a new immutable revision for the repair, and re-audit before making any normality or calculation-readiness claim.
- An abnormal model may be hot-loaded into the verified single existing Materials Studio window for explicit visual review, but the response must mark it as visual-review-only and must not imply that the model is normal or calculation-ready.
- Treat `dopant_site_summary.metadata_consistent=false` or `stale_site_count>0` as a structural consistency blocker. Do not claim the model is normal or calculation-ready; reconcile the concrete dopant-site metadata with the current atom table, export diagnostics again, and verify the blocker is gone.
- Use `material_studio_project_reconcile_dopant_metadata` for that blocker only after explicit user confirmation because it writes a metadata-only revision, even in preview mode. It must prove `structure_unchanged=true` and `simulation_unchanged=true`, avoid an empty revision when the metadata is already consistent, and hot-load only after explicit execute intent. A user-requested structural patch that restores the declared dopant is also valid and must create a separate revision.
- If a precise follow-up is routed through `material_studio_live_modeling_request` without `project_id`, rely on its latest-project resolution only when the response includes `project_resolution`; surface that resolved project/revision in the user-facing result.
- For precise follow-up natural-language edits, let `material_studio_live_modeling_request` infer supported patch commands first: delete/substitute/move atom, add atom at explicit coordinates, add/delete bond, set bond type, or replace a bonded site with nitro/hydroxyl/amino/methyl functional groups.
- Natural-language repair requests such as `repair current dopant metadata`, `修复当前掺杂位点元数据`, and `清理失效掺杂记录` should route to `reconcile_dopant_metadata`; do not edit an existing revision in place.

## GitHub Workflow
- Publish substantial, independently reviewable capability or safety milestones through `Wqeeeeeeee/ms_mcp` pull requests.
- Branch from the latest `origin/main` with a `codex/<topic>` name, make focused commits, push the branch, and open a draft PR after validation.
- Never push directly to `main` or force-push shared branches.
- Do not commit the active `.codex/config.toml`, workspace revisions/jobs/screenshots, GUI captures, temporary probes, or test caches.
- Do not create a PR for a no-op or a trivial documentation-only correction unless the user explicitly requests it.

## Done When
- Structure is generated or imported.
- Pre-validation passes or explains exactly why it failed.
- MaterialsScript job is executed or failure is diagnosed when execution was requested.
- Live GUI workflows open or attempt to open the generated structure through a workspace `.stp` project wrapper in Materials Studio.
- View-audit diagnostics export model health, standard view parameters, warnings/errors, and GUI artifacts when available.
- View-bundle diagnostics export JSON plus CSV tables for external or scripted model inspection.
- `modeling_health` is returned for live and standalone view-audit workflows with a verdict, checks, errors, warnings, and next action.
- Reports contain convergence status when available, warnings, errors, and the next action.
