# Materials Studio Agent Rules

## Goal
Build reproducible Materials Studio modeling workflows through MCP tools, with optional live GUI loading into the currently open Materials Studio session.

## Hard Rules
- Prefer MaterialsScript and file-based workflows for structural changes.
- Use GUI control only when the user explicitly asks for the open Materials Studio GUI or real-time visual feedback.
- Prefer `material_studio_gui_*` tools for GUI preflight, activation, snapshots, opening structures, and Copy Script assistance.
- Treat every preview-to-execute apply handoff as revision-bound: preserve `expected_revision`, `working_dir`, `verify_ms_roundtrip`, explicit Fit-to-View/replay flags, and selected `views`; an apply tool must reject a stale `expected_revision` before probing the GUI or starting execution. Execute payloads remain confirmation-gated.
- A read-only `material_studio_gui_apply_current_revision` preview may preserve an already-loaded current revision only when a fresh GUI status proves exactly one Materials Studio process/window, exact project/revision wrapper provenance, matching controller workspace and planned structure path, and the revision has a successful persisted result with an existing structure artifact. Treat `hot_loaded_from_live_status=true` as observation of prior state only: the preview must report that it invoked no runner, materializer, GUI input, reopen, or process launch. A hidden, minimized, or background target does not erase an otherwise exact loaded-revision binding, but it must set `interaction_ready=false`, preserve the activation blockers, and forbid snapshots or GUI input until the same window is restored and verified foreground. Any failed result, stale/mismatched wrapper, missing artifact, fallback window selection, or multi-window state blocks loaded-revision recovery.
- Modeling-health recomputation may suppress the legacy `GUI hot-load was not performed` warning only from fresh `material_studio_live_status_hotload_evidence_v1` generated for the same response. Require its successful result, exact project/revision/planned-structure binding, one process/window, target identity, empty binding blockers, and observation-only/no-side-effect fields before setting `gui_hot_loaded_from_live_status=true`. Treat `interaction_ready` and `interaction_blocking_reasons` as a separate GUI-action gate; they do not change which immutable revision is loaded. This prevents a status refresh or diagnostic export from failing an otherwise-satisfied `ModelSpec.acceptance` solely because an older report lost `gui_open` or the exact target was minimized. Absent, stale, failed, forged, or mismatched binding evidence retains the existing warning or preview gate.
- A combined modeling or session request may set `fit_to_view_after_open=true` or include an explicit Fit-to-View phrase. Preserve the structural `spec`/`patch` plan or the selected `show_current`/`rollback`/`redo`/`restore` workflow, and run framing only after explicit `execution_mode=execute`, successful revision execution, and verified same-window hot-load. A request that explicitly reloads, opens, shows, or pushes the current revision before framing must remain `show_current`; a pure Fit-to-View request must not rematerialize the structure. Preview must return `post_hotload_fit_to_view.status=deferred_until_execute` without GUI input. Open, Fit-to-View, final snapshot, and report publication must share the same revision's GUI artifact transaction. Trust completion only when `post_hotload_fit_to_view.completed=true`, `structure_unchanged=true`, and the final snapshot is bound; a blocked action is partial success and must be retried with its exact Fit-to-View payload without rerunning the structure.
- A combined create, patch, `show_current`, rollback, redo, restore, or direct apply request may set `prepare_view_replay_after_open=true`. When that parameter is omitted, infer it only from an explicit GUI hot-load/open request that also supplies a view subset or asks for a normality check; explicit `false` always suppresses inference. Preview and `open_in_gui=false` must return a stable deferred/not-run `post_hotload_view_replay_prepare` receipt without opening or changing the GUI. After execute, prepare the exact current revision only after successful same-window hot-load and after releasing the GUI artifact report transaction; recheck current immediately before preparation and again after the replay controller returns. If current advances during preparation, preserve the old manifest as historical evidence, publish no old `view_replay_continuation`, and route only to a workspace-bound current-project status refresh. On success, expose replay through `visual_diagnostics_next_action_plan` and `coordinated_next_action_plan` while preserving the existing `next_action_plan` as the modeling/calculation authority. Preparation creates no revision, sends no GUI input, does not accept any view, and must not rewrite the already published modeling report. A preparation failure is partial success: preserve the structure and hot-load evidence and return an exact workspace-bound `material_studio_gui_prepare_view_replay` retry payload without rerunning or reopening the model.
- For crystallographic or semiconductor viewport replay, call `material_studio_gui_prepare_view_replay` first. It only persists camera/projection parameters and safety state; it does not modify the GUI.
- Static command registry/help evidence is not enough for automatic Cartesian or isometric replay. Submit `material_studio_gui_prepare_view_replay.runtime_accessibility_evidence` only after refreshing the accessibility tree on the exact current revision/window. Reset and, for isometric replay, Movement must either be exposed with their exact expected names and support invocation or be derived by the server from `anonymous_toolbars`: the installed `#SVViewer3d.xml` SHA-256, exact allowlisted toolbar identity, full direct-child count/order/roles, separator positions, and fresh UIA element indexes must all match. The client may report only observations; it must not assert a command-to-index mapping. Use an unnamed element only when the returned recipe has `target_kind=verified_anonymous_toolbar_child`, `automation_ready=true`, and the same fresh tree still matches immediately before invocation. Record the exact `accessibility_command_uses` receipt afterward. Missing, stale, disabled, reordered, extra, or client-guessed anonymous controls remain blocked and route to reviewed manual or Copy Script handling. Keyboard recipes also require an observed document and a visually verified empty viewport focus target. Never use toolbar coordinates.
- `material_studio_gui_execute_view_replay` is the optional local-UIA executor for exactly one `front`, `back`, `right`, `left`, `top`, `bottom`, reviewed `isometric`, or automation-ready Miller-plane recipe. It defaults to `execution_mode=preview`; only an explicit `execute` may change the GUI. Cartesian/isometric execution may invoke Reset View and send the recipe's exact unmodified arrows to the unique `CViewer3DCtrl`. Isometric execution must additionally invoke the freshly verified Movement target, require the exact owned `Movement` window and `MovementOptions` pane, use only the unique `numNudgeAngle/TextCtrl` ValuePattern, prove every `cmdNudge*` button is disabled, keep `numNudgeFactor=2.0`, close Movement before every viewport stage, and restore/persist `numNudgeAngle=45.0` before returning. Transactional Miller execution must capture the pre-action viewport, forbid Reset, verify `Alt+T`, `M`, `MillerPlanesCtl`, `TxtHKL`, `CmdCreate`, Properties Explorer, and the installed numeric View Onto mapping; derive the only allowed pointer click from fresh before/after viewport pixels; capture the aligned view; then undo exactly `Undo View Onto Miller Plane` and `Undo Create Miller Plane` and prove exact viewport plus structure-SHA restoration. Every path must refresh and bind the exact wrapper, installed command registry, foreground state, and semantic viewport before input. It never uses blind or stale coordinates, never holds viewport modifiers, and never launches another MS process.
- `semantic_viewport_focus_supported=true` is valid only when generated by the local UIA backend after finding one enabled, visible, keyboard-focusable `CViewer3DCtrl`; clients must not submit it as observed evidence. A local execution receipt proves only the bounded mechanical transaction and unchanged structure SHA-256. For Miller replay it may persist the aligned pre-cleanup screenshot and exact cleanup/runtime evidence, but it must still leave model visibility and final camera acceptance unconfirmed, create no replay event, and require Computer Use or human review before `material_studio_gui_record_view_replay`.
- A verified automatic-recipe invocation that fails the visual camera/model postcheck must not be retried automatically with the same semantic mapping. A failed verified `front` Reset baseline also blocks automatic keyboard/isometric recipes that depend on that exact Reset mapping; route them to reviewed Copy Script or manual GUI review until later success evidence with verified artifact integrity supersedes the failure. Preserve all replay events when re-preparing a different view subset for the same immutable revision.
- After Computer Use, reviewed Copy Script, or human review applies a prepared view, call `material_studio_gui_record_view_replay` for that exact view. Do not treat the replay as accepted unless the returned target revision identity and single-window gates pass.
- Treat pre-action replay instructions and post-action evidence as separate contracts. For `automatic_recipe_ready`, use only `replay_continuation.execution_action` after its safety gate passes. A locally supported Miller transaction may return `recommended_mcp_tool=material_studio_gui_execute_view_replay`, `execution_mode=preview`, `payload_hint_is_directly_callable=true`, and `gui_input_required=false`; this authorizes only the read-only preview, and its returned confirmation action still requires explicit execute intent. For external replay, `payload_hint_is_directly_callable=false` means the recipe instructions are not an MCP record call. The `post_action_record_payload_template` deliberately leaves observed success, screenshot, camera, keyboard, accessibility-invocation, and Miller-plane fields null. Refresh the exact window/accessibility state, perform the recipe, capture fresh evidence, replace every required null from observation, and only then call `material_studio_gui_record_view_replay`. Never copy expected recipe values into observed fields or record evidence before GUI input finishes.
- Treat `material_studio_live_capabilities.view_replay_automation_policy.local_uia_implementation_contract` as static implementation discovery, not runtime permission. With `include_status=true`, require `view_replay_runtime_availability` and the compact `gui_status` receipt before selecting the local executor. Miller-plane and exact-collinear direction execution require both runtime transactional-Miller support and the current prepared recipe's `automation_ready=true`; non-collinear directions remain reviewed-camera-backend gated. The legacy broad direction-review boolean is conservative and its declared scope is `non_collinear_only`.
- When `source="reviewed_copy_script"`, supply `reviewed_copy_script_evidence` with the exact inert Materials Studio Copy Script text and completed review attestations, plus an exact window handle/title binding and a workspace screenshot. The server must never execute that script. It may persist the raw script only when static checks find no shell, network, file import/export/delete, calculation, or structure-mutation signals; otherwise persist only its SHA-256 and rejection analysis. Missing or unsafe Copy Script evidence must not accept the view or upgrade visual confirmation.
- Treat accepted replay history and currently trusted replay evidence as separate states. Every new reviewed Copy Script event must bind SHA-256 digests for its screenshot, inert script, metadata, and structure artifact. Live status, manifest refresh, GUI report rewrites, and every same-revision modeling-health report rewrite must reverify those files and the exact current diagnostic view set. An apply-current request with `views` omitted preserves the bound replay view set before the persisted audit or domain defaults; an explicit view list may invalidate prior trust. Missing or changed evidence preserves the append-only event but removes that view from trusted acceptance, invalidates its derived visual confirmation and persisted trusted summary, and requires fresh evidence.
- Reconcile every new replay event between `gui_view_replay_manifest.json` and the durable append-only `gui_view_replay_events.jsonl`. The immutable event digest excludes current verification fields but binds the recorded payload. A missing, duplicate, or mismatched journal copy must not count as trusted acceptance or visual confirmation. Read-only status must report the divergence without copying events between files; recovery requires a new observed event.
- Treat `prepare_view_replay` and `record_view_replay` as one serialized write domain per project/revision. Their kernel-managed transaction lock must cover manifest read, evidence persistence, journal append, and manifest publication so concurrent MCP calls cannot lose events or overwrite a newer manifest. A lock timeout must fail before appending an event; never bypass or delete an active lock file.
- Serialize GUI open, snapshot, and visual-confirmation report persistence together per project/revision. The shared GUI artifact report lock must cover reading prior GUI artifacts, applying open-reset or evidence-append semantics, re-auditing, and atomically publishing `report.json`; concurrent updates must follow lock acquisition order without losing evidence. When they resolve a structured project/revision, direct `material_studio_gui_activate(take_snapshot=true)`, `material_studio_gui_snapshot`, `material_studio_gui_open_structure`, and `material_studio_gui_record_visual_confirmation` calls must acquire that lock before target-window revalidation, GUI action, or evidence binding and hold it through report publication. High-level create, patch, and apply-current execute paths must leave MaterialsScript execution or crystal materialization outside this GUI lock, then acquire it before fresh current-revision and single-window preflight checks and hold it through GUI open, optional snapshot, and final report publication. A revision superseded during execution must return `current_revision_hotload_block` and must not be opened. Internal report persistence reuses the active same-revision transaction; nested acquisition for a different project/revision must fail. A direct-action report-lock timeout prevents the GUI action from starting. A high-level timeout after execution preserves the generated structure and committed report, returns `report_persistence_deferred=true` plus `gui_open_retry_tool`/`gui_open_retry_payload`, and must not open the GUI; retry that exact open after the active transaction finishes. Never delete the lock file. Keep this lock distinct from the controller replay lock to avoid nested-lock deadlocks.
- High-level `show_current`, natural-language patch, rollback, redo, and restore workflows must inject their final orchestration metadata before the nested apply/update call publishes diagnostics. The persisted `modeling_report` and `report.json` must be final while the matching GUI artifact transaction is still active; never add a second post-lock `_persist_modeling_report` write that can overwrite concurrent snapshot or visual-confirmation evidence.
- `material_studio_model_export_view_audit`, `material_studio_model_export_view_bundle`, and high-level `inspect_current` must use the same GUI artifact report transaction for persisted revision diagnostics. Acquire it before rereading prior GUI artifacts or probing/capturing the target window, revalidate that a current-project request still points to the same revision, and hold it through bundle plus `report.json` publication. This requirement still applies when `include_gui_snapshot=false` because diagnostic files and reports are writes. A busy lock must return `diagnostic_export_deferred` plus an exact retry payload without capturing or overwriting anything; a superseded current revision must return `diagnostic_export_current_revision_block`. Inline specs use the same output lock and must not replace a conflicting immutable stored revision.
- Serialize each project's revision allocation and publication with `project_state.lock`. The state transaction covers immutable spec/script writes, atomic `history.jsonl` replacement, and atomic `current.json` replacement. Patch and rollback callers must commit against both the current revision they read and the exact new revision used to prepare scripts and output paths; a current-revision or orphan-safe allocation mismatch must fail with a refresh/retry receipt and must not silently renumber prepared artifacts. Treat this as serialized, per-file atomic publication rather than a cross-file database transaction: an interrupted write may leave immutable orphan files, which must never be overwritten or deleted.
- Serialize each persisted project/revision execution with `outputs/rNNN/revision_execution.lock`. Bind the request to the immutable stored spec, acquire the lock only after releasing `project_state.lock`, revalidate that the revision is current before starting MaterialsScript or CIF materialization, and hold it through the single atomic publication of canonical `result_metadata.json`. A lock timeout must return `revision_execution_busy` without starting a second runner; a revision that advanced while waiting must return `current_revision_execution_block` without execution. If current advances during an already-running job, preserve the immutable result and set `current_revision_still_current=false`; the later GUI gate must refuse to hot-load it. The strict order is project state lock, release, revision execution lock, release, then GUI artifact/report lock. Never acquire these domains in reverse order or delete a persistent lock file.
- Every persisted revision execution must publish a unique durable attempt. Before invoking the backend, append a hash-linked `started` event to `execution_attempts.jsonl` and atomically refresh the derived `execution_attempt_state.json` cache when possible; the journal remains authoritative if cache publication fails. Bind project/revision, PID, backend, immutable spec SHA-256, exact saved script SHA-256, lock path, and planned structure, and reject execution before the attempt if the saved script differs from the deterministic translator output. Append a terminal `completed` or `failed` event and, when canonical result publication succeeds, include the same terminal `execution_attempt` in `result_metadata.json`. Never truncate, edit, or silently reconstruct the journal. `material_studio_live_project_status.execution_runtime` must probe the kernel lock before and after reading attempt state and classify `running`, `running_unrecorded`, `running_identity_mismatch`, `completed`, `failed`, `interrupted`, `transitioning`, `history_invalid`, `identity_mismatch`, `result_missing`, or `legacy_completed`. Automatic execution retry is never allowed from status alone: poll only clean running/transitioning work, and require explicit reviewed execution intent after failed/interrupted states. Preserve all artifacts when history, identity, or result publication is inconsistent.
- For recurring 20-minute project monitoring, use `material_studio_live_watchdog_status` with the current `project_id`, `expected_revision`, and prior `state_fingerprint`. It is a bounded read-only projection of the authoritative full project status. Only its exact `poll_action` may be called automatically and only when `automatic_call_allowed=true` with the payload present; every modeling, calculation, detail, activation, replay, or other non-poll action remains non-automatic even when the underlying status calls it safe. A revision mismatch must preserve the caller's old `expected_revision`, and a state change must be reviewed before adopting a new target. Never infer execution retry permission from the watchdog.
- When a restricted @mcp allowlist exposes only the high-level entry, persist prepared-view evidence through `material_studio_live_modeling_request.view_replay_confirmation`. Supply the view name, observed current revision, exact window handle/title, camera-manifest result, and the reviewed native command ID when one was used. A binding mismatch must not append a replay event or create a revision.
- Read each prepared view's `execution_recipe` and the manifest/status `replay_continuation` before GUI input. Automatic replay is allowed only when `automation_ready=true`. In Materials Studio 20.1, the verified face recipes are: `front` = named Reset View; `back` = Reset + unmodified `Left x4`; `right` = Reset + `Up x2, Left x2`; `left` = Reset + `Up x2, Right x2`; `top` = Reset + `Up x2`; `bottom` = Reset + `Left x4, Down x2`. The verified isometric recipe is Reset, then `45 degrees: Up x2, Left x3`, then `35.26438968 degrees: Down x1`; it must finish with A left-down, B right-down, C up, restore `numNudgeAngle=45`, preserve `numNudgeFactor=2.0`, and close Movement. Record exact `keyboard_stages`, reset/restoration/control evidence, and `modifier_keys=[]`. Never hold Shift: MS documents Shift+arrow as rotating selected objects, which changes geometry. `crystal_plane_*` may be automatic only when the returned recipe verifies the installed Miller Plane, Properties Explorer, View Onto, and one exact semantic plane-selection profile. Use the Object Tree before/after leaf path only when that explorer is actually exposed. In MS 20.1, where the installed Object Tree component is hidden and Project Explorer contains project documents rather than structure objects, use the verified viewport profile only after fresh before/after screenshots isolate one unique transient-plane region; select it with no modifiers, verify `Filter=Miller Plane` and the exact Miller label in Properties Explorer, and invoke native View Onto only after live toolbar numeric mapping confirms command `33297`. Never substitute Project Explorer or reuse old coordinates. Capture the pre-action viewport without Reset, create exactly one transient plane, capture the aligned view, then undo exactly `Undo View Onto Miller Plane` followed by `Undo Create Miller Plane`; no Reset or Recenter cleanup is allowed. Prove the document, temporary-plane state, exact viewport baseline, and structure SHA-256 were restored. Record `miller_plane_evidence`; treat the camera match as plane-normal plus MS native smallest-acute-angle roll, not exact analytic `camera_up`/`camera_right`. A `crystal_*` lattice-direction view may use the same transient-plane path only when its recipe reports `exact_integer_plane_collinear`; use the returned mapped Miller indices, require `direct_lattice_direction_matches_manifest=true`, and never assume same-index `[uvw]=(hkl)`. Non-collinear directions remain reviewed-camera-backend gated. Never substitute continuous Spin/Roll/Rock, `cmdNudge*`, object-align commands, or blind trackball drags.
- For crystal `front/back/right/left/top/bottom/isometric`, interpret `camera_matches_manifest` as the requested view direction plus the observed Materials Studio native in-plane roll, not exact equality with the analytic audit `camera_up`/`camera_right`. Record a fresh workspace screenshot and strict `crystal_camera_evidence` with `view_direction_matches_manifest=true` and `native_in_plane_roll_observed=true`; `analytic_in_plane_basis_matches_manifest` is required but may be `false` or `null`. Molecule standard views keep their existing camera contract. A crystal event recorded under an older recipe schema remains append-only history but is not accepted for the current recipe until fresh evidence is recorded.
- Miller View Onto automation never uses Reset. The local transaction captures the pre-action camera baseline and may generate exact-bound `runtime_ui_evidence` during execution after revalidating the current wrapper, semantic viewport, dialog controls, Properties selection, and live native command mapping. Externally supplied runtime evidence remains valid only when it binds the exact current revision/window and complete selection profile. A generic front Reset camera mismatch blocks Reset-dependent standard views but must not block a Miller recipe whose `camera_result_depends_on_reset_baseline=false` and final command is `cmdViewer3DViewOnto`.
- Static Materials Studio registry/help evidence is not sufficient for automatic Miller-plane replay. For external/manual preparation, submit `material_studio_gui_prepare_view_replay.runtime_ui_evidence` only after observing the exact current revision/window, Tools > Miller Planes, dialog, Properties Explorer, View Onto mapping, and either an exact Object Tree item or the complete viewport-selection probe. The local transactional executor may instead verify and persist that evidence atomically while executing. The viewport probe must bind the exact current structure artifact, equal before/after/current SHA-256 values, fresh screenshot-derived hit testing, Properties verification, native View Onto command `33297`, and exactly the two observed undo labels. The evidence must bind the current revision, window handle/title, and single-window state. In MS 20.1 invoke Tools > Miller Planes only with the verified keyboard mnemonic sequence `Alt+T`, then `M`; never use a pointer or accessibility menu click because the release can click through into the modeless dialog and activate Create. Once the dialog appears, target `TxtHKL`, `CmdCreate`, and its close control only from a fresh modeless child-window state: use an accessibility element verified inside the child bounds or a fresh child-screenshot coordinate, never a parent-window coordinate or an out-of-bounds duplicate element. Never assume `Ctrl+A` replaced `TxtHKL`: prefer exact accessibility `set_value`; otherwise use the recipe's fresh-value correction order. From any fresh readback, first repair a verified affix relation from `Home`, replace only a differing suffix from `End`, or preserve the longest common contiguous substring and apply exactly one nonempty edge repair in observed-prefix, observed-suffix, expected-prefix, expected-suffix order. Follow the recipe timing fields exactly: wait `200 ms` after `Home`/`End`, never batch repeated `Backspace`/`Delete` events, wait `200 ms` between each destructive key, and wait `500 ms` after mutation before the next fresh child readback. Replan from that readback after every mutation. Make at most one observed-character-count full replacement; after it, only those relation-based repairs remain allowed and an unrelated value must abort. Do not use Shift or a selection range. Require an exact trimmed-text match with `dialog_miller_indices_text` before Create. Record the observed text, `fresh_modeless_child_accessibility_value` source, and verified-before-create boolean in `miller_plane_evidence`; a mismatch blocks Create. If an unexpected default plane appears, invoke only the exact named `Undo Create Miller Plane`, prove cleanup and a clean document, and abort that replay attempt.
- For the verified MS 20.1 Miller transaction, bind document cleanliness to the internal viewer document title (`model_*.cif` / `model_*.cif *`), not only the outer wrapper title. The owner-drawn Properties Explorer menu may expose blank submenu labels, but it is callable only when the exact live command ID is `33439`. A virtualized `MillerIndex Record 0` row may report `is_visible=false`; accept it only under a visible Properties pane and visible `vGridControl`, with one unique `DataItem` whose exact value matches the prepared Miller label. On negative-coordinate monitors, derive the viewport from the visible ancestor chain `CViewer3DCtrl -> viewer pane -> document -> MDIClient -> exact target window`; every ancestor must remain visible and the chain must terminate at the expected handle. Compare only that intersection so status-bar/help text outside the MDI client cannot produce a false cleanup failure, and reject a too-small intersection. Do not relax the zero-pixel restoration requirement.
- On resumed sessions, read `material_studio_live_project_status.gui_view_replay` before replaying views; it reports the manifest, accepted-view progress, last event, and continuation action for the current revision.
- Use `material_studio_live_project_status.gui_view_replay.progress` as the stable full/compact replay-progress decision. Require `schema_version=material_studio_gui_view_replay_progress_v1`, current target project/revision, `binding_verified=true`, consistent accepted/pending counts, `all_supported_views_confirmed=true`, `evidence_integrity_status=verified`, `journal_consistency_status=consistent`, and `trusted_complete=true` before saying every diagnostic view is complete. The flat `accepted_view_count`/`accepted_view_names` fields are compatibility aliases only. A binding mismatch, contradictory count, integrity failure, or journal divergence must remain incomplete even when the manifest claims completion.
- A completed replay may satisfy only the live visual-review gate through `trusted_clean_view_replay.ok=true`. Require verified current project/revision binding, an exact replay-versus-diagnostic view-set match, all supported views confirmed under current recipes, the recommended clean view and every manual-review view confirmed, `evidence_integrity_status=verified`, and `journal_consistency_status=consistent`. The receipt may resolve only `view:projection_overlaps`, `view:view_warnings`, `gui:viewport_model_not_visible`, and `gui:viewport_capture_limitation_possible`; keep those as visual notes. It never resolves structure, semiconductor, acceptance, single-window, or calculation-readiness failures. Surface `resolved_visual_review_reasons` separately from `unresolved_visual_review_reasons`, and keep `ready_for_calculation` independent.
- A diagnostic re-export with `views` omitted must preserve the exact current revision's bound replay view set, otherwise the current valid persisted audit view set, before falling back to domain defaults. An explicit `views` list may intentionally change the diagnostic set and therefore may make existing replay evidence untrusted until those views are reviewed.
- Explicit continuation requests such as `continue the next GUI view replay`, `resume view replay`, `继续视角回放`, or `继续验证下一个 GUI 视角` should route through `material_studio_live_modeling_request` with `workflow=continue_view_replay`. That workflow may prepare/upgrade the manifest but never creates a revision or issues GUI input; execute a returned recipe only after inspecting its automation gate.
- Treat `gui_view_replay.recipe_contract` as an execution gate. A persisted pending recipe whose schema or required safety fields do not match the current runtime must report `replay_continuation.status=recipe_upgrade_required`; do not execute or record it. Route through `material_studio_live_modeling_request` with `workflow=continue_view_replay` to regenerate current recipes while preserving replay events. This manifest migration must not create a model revision or modify the structure. Historical `accepted=true` remains visible, but only evidence satisfying the current recipe counts in `accepted_view_names`; follow `current_camera_evidence_reverification_view_names` and record fresh crystal camera evidence before continuation.
- Use `gui_view_replay.next_action` only after its `next_action_resolution` has reconciled it with the current `replay_continuation`. When the resolution reports a continuation safety override, its resolved tool/action supersedes any persisted GUI activation or execution hint. In particular, `stale_recipe_execution_blocked=true` forbids activation-driven replay until the directly callable high-level recipe-upgrade action succeeds; status reconciliation itself is read-only and must not create a revision or modify the structure.
- Materials Studio 20.1 locally documents Reset/Recenter/View Onto/View Across/Fit-to-View but no arbitrary camera-vector MaterialsScript API. Do not invent one. A pre-activation screenshot can capture an occluding window, so activate and reverify the target wrapper before screenshot or input; never use an unverified unnamed toolbar control or a blind coordinate. The only unnamed-control exception is an exact server-returned `verified_anonymous_toolbar_child` recipe bound to the current revision/window and a freshly matching accessibility tree.
- When current-revision status reports `snapshot_viewport_likely_visible_model=false`, `snapshot_viewport_capture_limitation_possible!=true`, and `snapshot_viewport_capture_diagnostic="low_contrast_or_not_fit_to_view"`, follow the returned read-only `material_studio_gui_fit_to_view` preview only after the fresh single-window, exact-wrapper, selected/foreground, visible, and non-minimized gates pass. The preview may return an explicit execute confirmation action, but status orchestration must never execute it automatically. A capture limitation, stale revision, inactive target, or accepted external visual confirmation suppresses this recommendation and keeps the corresponding snapshot/review, reload, activation, or continue action authoritative.
- `material_studio_gui_status` may omit `project_id`/`revision`; when a latest current structured project exists, use its `project_resolution`, `target_window`, and `target_window_resolution` fields rather than assuming `selected_window_handle` is the current revision.
- GUI wrapper provenance lookup is bounded to the controller workspace, `MATERIAL_STUDIO_MCP_WORKSPACE`, and the platform default per-user workspace. Never broaden it to a drive-wide search. When `workspace_context_mismatch=true`, surface the visible wrapper's exact workspace/project/revision and `recommended_working_dir`; never adopt or write that workspace automatically.
- An omitted-project follow-up through `material_studio_live_modeling_request` must stop before any revision write when the visible Materials Studio wrapper belongs to another trusted workspace. ## GitHub Workflow
- Publish substantial, independently reviewable capability or safety milestones through `Wqeeeeeeee/ms_mcp` pull requests.
- Branch from the latest `origin/main` with a `codex/<topic>` name, make focused commits, push the branch, and open a draft PR after validation.

- Do not commit the active `.codex/config.toml`, workspace revisions/jobs/screenshots, GUI captures, temporary probes, or test caches.
